# A language the repo barely writes has no voice to be foreign to

**Date:** 2026-07-28 · **Status:** positive — one corpus's worst number went to
zero, recall unmoved, and the class of defect behind it is closed.

**Question:** rocksdb's new-file over-fire was **27/82 = 32,9 %** — by far the
worst number in the benchmark. What fires, and why there?

## What fires

Every one of the 27 is a machine-generated C++ file under `c_api_gen/`
(`// @generated`, "DO NOT EDIT THIS FILE DIRECTLY"), scored as **Pascal**.

`.inc` entered the global extension table with the Pascal port
(`7886a796`, 2026-07-20), after the last published run — which is why the
2026-07-14 dashboard shows 0/55 for the same pinned corpus. `.inc` is a Pascal
include extension. It is also a C, C++ and CMake one.

rocksdb's entire Pascal corpus is **one file**: `thirdparty.inc`, a CMake
include. The dashboard's per-language split is unambiguous:

```
pascal:  existing hunks 0,  hits 0
         new_file hunks 27, hits 27   →  rate 1.00
```

Zero training hunks, and every single new hunk flagged. Nothing is familiar to a
one-file model, so everything is foreign.

## The defect is not the extension table

Routing `.inc` per repo majority — the treatment `.h` already gets from
`ext_to_lang_ctx` — would fix rocksdb and leave the hole open for the next
ambiguous extension. The hole is that **a per-language scorer is built, and
allowed to gate, on arbitrarily little evidence.**

Measured across the 36 benchmark corpora, by per-language replayed-hunk count:

| language support | cells | false alarms |
|---|--:|--:|
| < 50 replayed hunks | 16 | **41/187 = 21,9 %** |
| ≥ 50 replayed hunks | 38 | **472/35 630 = 1,3 %** |

**17× worse.** And the file counts say the same thing from the other side: 35 of
97 language cells hold ≤10 files, 20 hold ≤3. Every one is incidental — one Ruby
file in castle-engine, one Rust file in dagster, one `.inc` in rocksdb, two each
of Go/Java/C#/PHP/C++ in bat, a Rust tool that ships syntax *samples*. None is a
language its repo writes. The degenerate cells fire on everything:
`rocksdb/pascal` 27/27, `curl/pascal` 2/2.

## The fix

`MIN_LANGUAGE_FILES = 10` at the calibration seam: below it a language gets no
scorer, and `check` abstains through the path it already uses for an unsupported
extension. No new branch downstream, and any future misrouting is harmless
rather than catastrophic. Ten matches `SLICE_AUTO_MIN_FILES`, the floor this
file already applies to directories.

**It never drops a language unless another clears the floor.** In a repo that is
simply small, the file count is the repo's size rather than evidence the
language is incidental — so a small single-language repo keeps its voice.

**It is never silent.** The skip is recorded in the manifest as
`unlearnable_languages` and printed at fit:

```
[argot] javascript: 3 files — too few to learn a voice (needs 10).
        Files in this language are NOT checked.
        With this little of a language, every construct reads as unfamiliar and
        the rule would fire on all of it. If an extension is routed to the wrong
        language here, exclude it in argot.toml.
```

Silence that means *not checked* must not read as silence that means *nothing
found* — the same lesson the scripted-rules budget defect taught
(`custom-rule-performance.md`).

## Results

Full 36-corpus honest bench, before and after:

| | before | after |
|---|--:|--:|
| novel-pattern catch (headline) | 647/756 = 85,6 % | **647/756 = 85,6 %** |
| worst new-file over-fire | **32,93 %** (rocksdb) | **22,73 %** (uos) |
| worst existing over-fire | 3,09 % (uos) | 3,09 % (uos) |
| corpora above 2 % over-fire | 1 of 36 | 1 of 36 |

Per corpus:

| corpus | new-file over-fire | after |
|---|--:|--:|
| rocksdb | 27/82 = 32,93 % | **0/35 = 0,00 %** |
| curl | existing 2/402 | **0/400** |

**Recall did not move.** The floor removes languages from every model, so the
run had to prove no catalogued fixture lived in one — none did.

## On comparing this run to the last published one

Aggregate over-fire reads 0,29 % (2026-07-14) → 0,60 % (2026-07-28), which is
not a regression:

| set | old | new |
|---|--:|--:|
| the 31 corpora in both | 66/24 850 = 0,27 % | **56/24 176 = 0,23 %** |
| the 5 Pascal corpora added since | — | 154/10 938 = 1,41 % |

On like-for-like corpora over-fire **improved** (guava 20 → 4, rocksdb 5 → 3).
The headline rise is entirely the Pascal corpora added after the July run, and
**uos alone contributes 108 of those 154**.

Denominators shift too, and legitimately: files in a language below the floor
are no longer scored at all, so a corpus's eligible-hunk count falls (rocksdb
2 230 → 1 697). Hunk-level comparisons across the floor are not like-for-like.

## What is left

**uos, 3,09 % existing over-fire (108/3 492) and 22,73 % new-file (5/22)** — now
the worst corpus in the benchmark and the only one above 2 %. It is Pascal, it
holds no catalogue fixtures, and it is not explained by this work.
